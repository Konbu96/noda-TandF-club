# 11. ユースケース詳細

> **確定した内容は [12. ユースケース決定事項](./12-decided-use-cases.md) を優先して参照。**

各機能を「誰が・いつ・何のために・どう使うか」まで具体化する。**要確認** 項目は [12章](./12-decided-use-cases.md) ですべて確定済み。本章はシナリオの参考資料。

## 11.1 記法

| 項目 | 説明 |
|------|------|
| **UC-ID** | ユースケース識別子（例: UC-M01） |
| **アクター** | 操作する人（部員 / キャプテン / マネージャー / 先生） |
| **目的** | この操作で達成したいこと |
| **トリガー** | いつ・何がきっかけで始まるか |
| **事前条件** | 始める前に満たしていること |
| **基本フロー** | 正常系の手順 |
| **代替フロー** | 分岐・例外 |
| **事後条件** | 完了後にシステム上どうなっているか |
| **優先度** | Must（初版必須）/ Should（早めに欲しい）/ Could（後回し可） |

### アクター略号

| 略号 | ロール |
|------|--------|
| M | 部員（member） |
| C | キャプテン（captain） |
| G | マネージャー（manager） |
| T | 先生・顧問（teacher） |

## 11.3 認証・共通

### UC-A01: ログインする

| 項目 | 内容 |
|------|------|
| **アクター** | M, C, G, T |
| **目的** | 自分の権限に応じた画面にアクセスする |
| **トリガー** | `/login` にアクセス、または未ログインで内部ページにアクセス |
| **事前条件** | Firebase Auth にアカウントが登録済み。`users` にロールが紐づいている |
| **基本フロー** | 1. メール/パスワード（または Google）でログイン<br>2. ロールを判定<br>3. 部員 → `/member`、管理者 → `/admin` へ遷移 |
| **代替フロー** | 認証失敗 → エラー表示。ロール未設定 → 管理者に連絡する案内 |
| **事後条件** | セッションが確立され、以降の操作がロールに応じて制限される |
| **優先度** | Must |
| **要確認** | ログイン方式（メールのみ / Google ログイン可） |

---

### UC-A02: ダッシュボードで今日の状況を把握する

| 項目 | 内容 |
|------|------|
| **アクター** | G, T（C は担当分のみ △） |
| **目的** | 練習前に「今日誰が休み・誰が体調注意か」を一目で把握する |
| **トリガー** | 練習当日の朝、管理者が `/admin` を開く |
| **事前条件** | ログイン済み。当日のスケジュール・休み・体調データが存在しうる |
| **基本フロー** | 1. ダッシュボードを開く<br>2. 「今日の欠席者」リストを確認<br>3. 「体調注意者」リストを確認<br>4. 直近の大会予定を確認<br>5. 必要なら個人ページへ遷移 |
| **代替フロー** | 欠席者0・体調注意0 → 「本日問題なし」と表示 |
| **事後条件** | 閲覧のみ（データ変更なし） |
| **優先度** | Must |

## 11.4 名簿・個人ページ

### UC-R01: 部員を名簿に登録する

| 項目 | 内容 |
|------|------|
| **アクター** | G, T |
| **目的** | 新入部員・転入者をシステムに登録し、以降の PB・休み・体調と紐づける |
| **トリガー** | 新年度・新入部、または途中入部 |
| **事前条件** | 管理者ログイン済み |
| **基本フロー** | 1. 名簿一覧 → 「部員追加」<br>2. 氏名・学年・性別・主種目等を入力<br>3. 保存<br>4. （任意）Firebase Auth アカウントを部員に発行し `memberId` と紐づけ |
| **代替フロー** | 必須項目未入力 → バリデーションエラー |
| **事後条件** | `members` に1件追加。公開サイトの部員数集計に反映（将来） |
| **優先度** | Must |
| **要確認** | 部員アカウントは誰が作成するか（管理者一括 / 初回ログイン時自己登録） |

| **事後条件** | 名簿が最新。卒部後も履歴（PB等）は保持（保持期間は要確認） |

### UC-R03: 名簿から個人ページを開く

| 項目 | 内容 |
|------|------|

| **トリガー** | 「A君の様子を知りたい」、練習前の確認、面談前 |

| **優先度** | Must |

## 11.5 自己ベスト（PB）

### UC-P01: PB を登録・更新する

| 項目 | 内容 |
|------|------|
| **アクター** | C, G, T |
| **目的** | 練習・大会での記録を残し、最新 PB を更新する |
| **トリガー** | 練習後のタイム計測、大会後の結果確定 |
| **事前条件** | 対象部員が名簿に存在。種目マスタに該当種目がある |
| **基本フロー** | 1. 個人ページまたは PB 管理画面を開く<br>2. 部員・種目・記録・計測日・公式/練習を入力<br>3. 保存<br>4. 既存 PB より良い記録なら「最新 PB」として反映 |
| **代替フロー** | 練習記録のみ → 履歴に追加するが最新 PB は更新しない設定も可（要確認） |
| **事後条件** | `personalBests` に履歴追加。個人ページのグラフ・サマリー更新 |
| **優先度** | Must |
| **要確認** | 部員の自己申告→承認フローを初版に含めるか |

---

### UC-P02: 個人の PB 推移を確認する

| 項目 | 内容 |
|------|------|
| **アクター** | M（自分）, C, G, T |
| **目的** | 種目ごとの成長・停滞を把握する |
| **トリガー** | 大会前の調子確認、面談、部員の自己確認 |
| **基本フロー** | 1. 個人ページ → 記録タブ<br>2. 種目を選択（例: 100m）<br>3. 期間フィルタ（3ヶ月/6ヶ月/1年/全期間）<br>4. 折れ線グラフと更新履歴表を確認<br>5. （任意）体調不良期間の帯表示をON |
| **代替フロー** | 記録0件 → 「まだ記録がありません」 |
| **事後条件** | 閲覧のみ |
| **優先度** | Must |

## 11.7 休み・欠席

### UC-X01: 休みを申請する

| 項目 | 内容 |
|------|------|
| **アクター** | M |
| **目的** | 練習に来られない日を事前に共有する |
| **トリガー** | 学校行事・体調・家庭都合などで欠席が決まったとき |
| **事前条件** | 部員ログイン済み |
| **基本フロー** | 1. マイページ → 休みタブ → 新規申請<br>2. 日付（単日 or 期間）・種別・理由（任意）・練習への影響を入力<br>3. 送信<br>4. ステータス「申請中」 |
| **代替フロー** | 体調不良種別 → 体調報告（UC-H01）と併用を推奨<br>締切後申請 → 承認は可能だが警告表示（締切時刻は要確認） |
| **事後条件** | `absences` に追加。管理者の承認待ち一覧に表示 |
| **優先度** | Must |
| **要確認** | 申請締切（前日 21:00 等） |

---

### UC-X02: 休み申請を承認・却下する

| 項目 | 内容 |
|------|------|
| **アクター** | G, T |
| **目的** | 欠席を正式に記録し、練習計画に反映する |

| **基本フロー** | 1. 休み管理 → 承認待ち一覧<br>2. 申請内容を確認<br>3. 承認 or 却下<br>4. 承認時、個人ページの休み集計・ダッシュボードの欠席者に反映 |
| **代替フロー** | 却下 → 部員に理由を通知（通知機能は Could） |
| **事後条件** | ステータス更新。当日なら「本日休み」バッジ |
| **優先度** | Must |

---

## 11.13 初版（Must）の範囲まとめ

9. 週間スケジュール + 今日の場所（UC-S01, S04）
10. 体調報告・管理者対応（UC-H01, H03）

**Should / Could** は Phase 2 以降で検討。
